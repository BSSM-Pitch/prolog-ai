이 레포지토리는 서비스 전체 구현이 아닌 ai기능만 구현하는 역할이다.

기획.md, db.md, api 명세 폴더의 내용은 사용자가 특별히 명령한 내용이 아닐 시 토큰을 절약하기 위해 보지 않는다.


# 작업 명령

너는 BSSM-Pitch/prolog-ai 저장소에서 공통 계약(에러 형식, 상태값, 필드 매핑, 공통 실행 뼈대, 모듈 스키마)을 설계하고 구현하는 역할이야.
이 작업은 팀원 두 명(Dev A, Dev B)과 함께 결정하는 작업이야. 그래서 아래 단계마다 반드시 멈추고 결과를 보고한 뒤, 내가 확인해 주면 다음 단계로 넘어가.
절대 여러 단계를 한 번에 진행하지 마.

## 배경

- 이 저장소는 Prolog 서비스의 AI 모듈 파이썬 패키지야. 백엔드(FastAPI)가 설치해서 함수만 호출해.
- 모듈: nlcd, rex, aiq (Dev A) / scds, ssm (Dev B)
- 폴더와 빈 파일은 이미 만들어져 있어. 각 파일 맨 위 docstring에 역할이 적혀 있어.
- 목표는 "완벽한 품질"이 아니라 "어떤 입력에도 정해진 형식으로 응답하고 절대 죽지 않는 것"이야.

## 절대 규칙

- docs/specs의 명세와 DB 설계 문서를 근거로만 결정해. 명세에서 확인할 수 없는 필드, 에러 코드, 상태값은 지어내지 말고 TODO로 남긴 뒤 보고해.
- 명세끼리 서로 안 맞는 부분을 발견하면 임의로 고르지 말고 보고해.
- 프롬프트 튜닝은 이번 작업 범위가 아니야.
- 실제 Claude API를 호출하지 마. 모든 테스트는 USE_FAKE_LLM=1로 돌아가야 해.
- main에 직접 push하지 마. feat/core-contracts 브랜치에서 작업하고, 단계마다 커밋해.

## 진행 규칙 (5단계 이후는 이 규칙이 위 "절대 규칙"의 브랜치 항목보다 우선)

- 단계마다 main에서 새 브랜치(`feat/<내용>` 또는 `fix/<내용>`)를 만들고, 커밋 → push → main으로 가는 PR 생성까지 한다.
- PR을 만든 뒤 AskUserQuestion으로 질문하고 멈춘다. 사용자가 "병합 완료"라고 하면 PR 병합 여부를 gh로 확인하고 main을 최신화한 뒤 다음 단계로 간다.
- 사용자의 선택이 필요한 결정은 글로 제안만 하지 말고 AskUserQuestion 선택지로 묻고, 답에 따라 바로 실행한다.
- 진행 과정은 한국어로 알린다.
- core/ 아래를 바꾸는 PR은 Dev A·Dev B 모두 확인이 필요하다고 PR 본문에 적는다.
- 위 절대 규칙(명세 근거로만 결정, 지어내지 않기, 실제 API 호출 금지, 프롬프트 튜닝 범위 밖)은 그대로 유지한다. 실제 API 호출은 9단계에서 사용자가 명시적으로 허락한 경우에만 예외로 한다.

## 5단계: 입력 방어 보강 + 다섯 모듈 가드레일 일괄 테스트 (Day2 오후 항목, R1·R5)

1. 방어 보강
   - 다섯 공개 함수 모두 입력 타입이 틀려도 죽지 않고 `INVALID_INPUT`으로 반환하게 한다 (문자열 자리에 None·숫자, dict 자리에 None·리스트 등).
   - SCDS의 룰 검출·SSM의 청킹·병합처럼 `run_module` 밖에서 도는 코드도 예외가 나면 errors.py 형식으로 반환하게 한다. 방법(공개 함수 공통 데코레이터로 감쌀지, 함수마다 처리할지)은 설계안으로 먼저 보고한다.
   - 타입이 틀린 입력이 `AI_*_FAILED`로 잘못 분류되지 않게 한다.
2. 가드레일 일괄 테스트: `tests/test_guardrails_modules.py`
   - 다섯 실제 함수 × 공통 시나리오를 파라미터화해서 한 번에 돌린다: 빈 입력, 공백만, 아주 긴 입력, "이전 지시를 무시해" 인젝션, 스토리와 무관한 문장, 잘못된 타입, LLM 예외, LLM 타임아웃, 스키마에 안 맞는 응답, 원문에 없는 근거
   - 모듈별 추가 시나리오: SCDS(world_rules 없음 → skipped, 후보 없음 → no_candidate이며 LLM 미호출 확인), SSM(여러 챕터 중 한 청크만 실패), AIQ(selection_range 누락·역전·원고 길이 초과)
   - 모든 경우 결과가 `{"data", "meta"}` 또는 `{"error": {"code", "message", "details"}}` 둘 중 하나이고, code가 ErrorCode에 있는 값인지 공통 검증 함수로 확인한다.
3. pytest, ruff 통과 확인 → 커밋 → PR → 멈춤.

## 6단계: 팀 결정 사항 확정 (코드 작성 금지, R2·R3·R4)

1. 결정이 필요한 항목을 하나씩 AskUserQuestion으로 묻는다. 한 번에 최대 4개, 항목마다 명세 근거와 선택지·장단점을 붙인다.
   - SCDS: RULE-01/03/04 판정 방식 (가치관별 위반 키워드 사전을 둘지 / LLM에 맡길지 / 이번 범위에서 제외할지), severity 판정 기준
   - NLCD: character_name 추출 여부, `duplicate_of` 판정 주체(AI 패키지 / 백엔드)
   - REX: source_chapter를 채우는 주체
   - SCDS: related_chapter_ref 생성 여부
   - SSM: 분량 부족 기준, 챕터 경계 기준, 청크 하나가 실패했을 때 처리 방식, character_ids 매핑 방식
   - 공통: 내부용 코드(`AI_TIMEOUT`, `SCHEMA_VALIDATION_FAILED`)를 밖으로 노출할지 모듈별 `AI_*_FAILED`로 바꿔 보낼지, 노출한다면 HTTP 상태
   - AIQ: 답변에 근거 대조를 적용할지
2. 명세끼리의 모순과 DB·API 불일치(DB 상태값 open/resolved·planted·draft, evidence·emotion_keywords 저장 컬럼 없음, SSM 결과 JSON 구조 차이, 챕터 int/uuid 차이)는 이 저장소가 정할 수 없으므로 "백엔드 팀 확인 필요" 목록으로만 정리한다.
3. 결정 결과와 백엔드 확인 목록을 `docs/specs/decisions.md`에 기록한다 (항목, 결정, 근거, 결정일, 미결정이면 담당자).
4. 문서만 커밋 → PR → 멈춤.

## 7단계: 결정 반영 (R3·R4)

- 6단계에서 결정된 항목만 코드에 반영하고, 해당 TODO 주석을 지운다. 미결정 항목의 TODO는 decisions.md 항목을 가리키게 바꾼다.
- SCDS 룰을 사전 방식으로 정했다면 사전은 코드와 분리된 데이터 파일로 두고, 사전 내용 자체는 지어내지 않고 팀이 준 값만 넣는다.
- 스키마가 바뀌면 test_modules.py, test_guardrails_modules.py를 같이 고친다.
- pytest, ruff → 커밋 → PR → 멈춤.

## 8단계: 실제 LLM 호출 경로 검증 (API 호출 없이, R6)

- `anthropic.Anthropic`을 monkeypatch한 가짜 클라이언트로 `_call_real_llm`을 테스트한다: tool_use 블록 파싱, tool_use 없는 응답, 타임아웃 후 재시도, 최대 재시도 초과 시 LLMTimeoutError·LLMFailedError, 인증 오류처럼 재시도하면 안 되는 오류.
- `PROLOG_AI_MODEL`·`ANTHROPIC_API_KEY`가 비어 있고 `USE_FAKE_LLM`도 아닐 때 어떻게 할지(즉시 에러 반환 권장)를 설계안으로 보고하고 확인받은 뒤 구현한다.
- 테스트 중 재시도 대기(sleep)가 실제로 걸리지 않게 한다.
- pytest, ruff → 커밋 → PR → 멈춤.

## 9단계: 평가(evals) 기반 마련 (R7)

- `evals/cases/<모듈>/`에 넣을 케이스 형식(JSON: 입력, 기대 조건)을 설계안으로 먼저 보고한다.
- 케이스 내용은 명세에 있는 예시(피터 파커, 계약 마법, 벤 삼촌의 죽음 등)만 사용하고 지어내지 않는다. 추가 케이스는 팀이 준 것만 넣는다.
- `evals/run_evals.py`는 기본값이 가짜 LLM이며, 형식·근거 대조만 채점한다.
- 실제 API로 품질을 보는 실행은 사용자가 명시적으로 허락할 때만 한다. 허락받으면 호출 횟수를 미리 알리고 최소로 돌린다. 결과는 커밋하지 않고 보고만 한다.
- 커밋 → PR → 멈춤.

## 10단계: 래퍼 포장 + 인수인계 (Day2 저녁 항목, R8)

- README에 추가
  - 다섯 공개 함수의 시그니처와 성공·실패·건너뜀 응답 예시
  - 에러 코드 → HTTP 상태 표 (`core/errors.py`의 HTTP_STATUS 기준)
  - 백엔드 작업(job) 상태와 연결하는 방법: 성공 → completed, error → failed, SCDS skipped/no_candidate는 그대로 기록
  - 환경변수 (`ANTHROPIC_API_KEY`, `PROLOG_AI_MODEL`, `USE_FAKE_LLM`)
- `docs/handoff.md`: TODO·미결정 목록(decisions.md 링크), 백엔드 팀 확인 목록, 알려진 한계(프롬프트는 자리표시 수준, 품질 미검증 범위)
- 버전을 올리고 태그를 만들지(`v0.1.0` 등) AskUserQuestion으로 확인받는다. 태그 push는 허락받은 경우에만 한다.
- 커밋 → PR → 멈춤 → 병합 후 최종 보고.

## 일정 조정안

원래 2일 계획은 "명세가 완전하다"는 전제라 결정 시간이 빠져 있었다. 남은 작업은 아래처럼 배치한다.

| 슬롯 | 단계 | 비고 |
| --- | --- | --- |
| Day2 오후 (공동) | 5단계 | 원래 계획의 "예외 케이스 일괄 실행" + 발견된 크래시 수정 |
| Day2 오후 끝 (공동, 1시간) | 6단계 | 팀 결정 회의. 결정 안 된 항목은 담당자와 기한만 정하고 넘어간다 |
| Day2 저녁 | 10단계 | 인수인계 문서를 먼저 끝낸다 (백엔드가 막히지 않게) |
| 후속 (버퍼) | 7 → 8 → 9단계 | 결정 반영, 실제 호출 경로 테스트, evals. 인수인계 이후에도 패키지 버전만 올리면 백엔드는 교체만 하면 된다 |

인수인계를 7~9단계보다 먼저 하는 이유: 인터페이스(공개 함수 시그니처, 응답 형식)는 이미 고정됐고, 7~9단계는 내부 동작만 바뀐다. 백엔드 연동을 막지 않는 것이 우선이다.
