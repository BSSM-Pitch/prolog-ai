이 레포지토리는 서비스 전체 구현이 아닌 ai기능만 구현하는 역할이다.

기획.md, db.md, api 명세 폴더의 내용은 사용자가 특별히 명령한 내용이 아닐 시 토큰을 절약하기 위해 보지 않는다.


# 작업 명령

너는 BSSM-Pitch/prolog-ai 저장소에서 공통 계약(에러 형식, 상태값, 필드 매핑, 공통 실행 뼈대, 모듈 스키마)을 설계하고 구현하는 역할이야.
이 작업은 팀원 두 명(Dev A, Dev B)과 함께 결정하는 작업이야. 그래서 아래 단계마다 반드시 멈추고 결과를 보고한 뒤, 내가 확인해 주면 다음 단계로 넘어가.
절대 여러 단계를 한 번에 진행하지 마.

## 배경

- 이 저장소는 Prolog 서비스의 AI 모듈 파이썬 패키지야. 백엔드(FastAPI)가 설치해서 함수만 호출해.
- 모듈: nlcd, rex, aiq (Dev A) / scds, ssm (Dev B)
- 폴더와 빈 파일은 이미 만들어져 있어. 각 파일 맨 위 docstring에 역할이 적혀 있어.
- 목표는 "완벽한 품질"이 아니라 "어떤 입력에도 정해진 형식으로 응답하고 절대 죽지 않는 것"이야.

## 절대 규칙

- docs/specs의 명세와 DB 설계 문서를 근거로만 결정해. 명세에서 확인할 수 없는 필드, 에러 코드, 상태값은 지어내지 말고 TODO로 남긴 뒤 보고해.
- 명세끼리 서로 안 맞는 부분을 발견하면 임의로 고르지 말고 보고해.
- 프롬프트 튜닝은 이번 작업 범위가 아니야.
- 실제 Claude API를 호출하지 마. 모든 테스트는 USE_FAKE_LLM=1로 돌아가야 해.
- main에 직접 push하지 마. feat/core-contracts 브랜치에서 작업하고, 단계마다 커밋해.

## 0단계: 명세 조사 (코드 작성 금지)

docs/specs의 모든 문서를 읽고 아래를 정리해서 보고해. 이 단계에서는 파일을 만들거나 고치지 마.

1. 에러 코드 목록: 모듈별로 등장하는 에러 코드, HTTP 상태, 의미. 공통 응답 형식도 원문 그대로.
2. 상태값 표: 아래 형식으로.
   | 모듈 | 동기/비동기 | 상태값 | 상태가 바뀌는 조건 | 특이사항 |
3. 모듈별 출력 필드: API 명세의 응답 필드와 DB 설계의 컬럼을 나란히 비교한 표. 이름이나 타입이 다른 곳은 표시해.
4. 모듈 간 필드 불일치: 특히 NLCD 출력(personality_tags, core_values, influence_relations, emotion_keywords)과
   SCDS 인물 모델(traits, values, influences)의 관계. 명세에 실제로 어떻게 적혀 있는지 확인해.
5. 명세에서 확인할 수 없어서 팀이 정해야 하는 것 목록.

보고하고 멈춰.

## 1단계: 에러 형식과 상태값

내 확인을 받은 뒤 진행해.

- core/errors.py
  - 명세의 공통 에러 형식 그대로: {"error": {"code": ..., "message": ..., "details": {}}}
  - make_error(code, message, details=None)
  - 0단계에서 확인한 에러 코드를 상수로 모아. AI 모듈 내부용 코드(AI_RESPONSE_FAILED, AI_TIMEOUT, SCHEMA_VALIDATION_FAILED, INVALID_INPUT)는
    명세에 없으면 "모듈 내부용"이라고 주석으로 구분해.
  - 성공 응답도 같은 파일이나 별도 헬퍼로 형식을 고정해: {"data": ..., "meta": {}}
- core/status.py
  - 0단계 상태값 표를 근거로 Enum을 만들어. 모듈마다 값이 다르면 공통 Enum 하나로 합칠 수 있는지 판단하고, 합칠 수 없으면 이유를 보고해.
  - "결과가 비어 있음"과 "참조 데이터가 없어 건너뜀"은 에러가 아니라 정상 상태라는 점을 코드 주석에 분명히 적어.
- tests/test_core.py에 두 파일에 대한 테스트 추가.

커밋하고, 결정한 내용과 판단 근거를 보고한 뒤 멈춰.

## 2단계: NLCD ↔ SCDS 필드 매핑

내 확인을 받은 뒤 진행해.

먼저 아래 세 가지 선택지를 명세 근거와 함께 장단점으로 비교해서 보고하고, 내가 고를 때까지 기다려.

1. NLCD 출력 필드명을 SCDS 이름에 맞춘다
2. SCDS 인물 모델에 필드를 추가해 NLCD에 맞춘다 (DB 변경이 필요하면 그렇다고 명시)
3. 변환 레이어(core/mapping.py)를 둔다

내가 고르면 그대로 구현해. 3번이면:

- core/mapping.py에 변환 함수를 만들고, SCDS에 대응 필드가 없는 항목(예: emotion_keywords)을 어떻게 처리하는지 docstring에 적어.
- 변환 테스트 추가.
  어떤 선택이든 README에 매핑 표와 결정 이유를 기록해.

커밋하고 보고한 뒤 멈춰.

## 3단계: 공통 실행 뼈대 (core/runner.py, core/llm.py, core/evidence.py)

내 확인을 받은 뒤 진행해.

먼저 설계안만 보고해 (코드 작성 전):

- run_module의 함수 시그니처와 각 인자의 역할
- 처리 순서: 입력 검증 → LLM 호출 → 스키마 검증 → 근거 대조 → 반환
- 다섯 모듈이 이 뼈대 하나로 모두 처리되는지 모듈별로 검토해. 특히:
  - SCDS: 룰 검출로 충돌 후보가 없으면 LLM을 부르지 않고 끝나야 하고, 참조 데이터가 없으면 건너뜀 상태로 반환해야 해
  - SSM: 긴 원고는 장 단위로 나눈 뒤 처리해야 해
- 뼈대가 책임질 범위와 각 모듈이 책임질 범위의 경계 (예: 청킹과 룰 검출은 뼈대 밖에서 하고 결과만 넘길지)
  내 확인을 받으면 구현해.

구현 요구사항:

- core/llm.py
  - Claude API 호출을 한 함수로 모아. 모델 이름과 API 키는 환경변수(PROLOG_AI_MODEL, ANTHROPIC_API_KEY)로 받아.
  - 타임아웃, 재시도(최대 2회), 출력 스키마 지정을 지원해.
  - USE_FAKE_LLM=1이면 API를 부르지 않고, 넘겨받은 스키마에 맞는 가짜 응답을 만들어 돌려줘.
- core/evidence.py
  - AI가 반환한 근거 문장이 입력 원문에 실제로 있는지 확인해.
  - 공백, 줄바꿈, 따옴표 종류 차이는 정규화해서 비교해.
  - 원문에 없는 근거를 가진 항목은 제거하고, 몇 개를 제거했는지 meta에 남겨.
- core/runner.py
  - 어떤 예외가 나도 죽지 않고 errors.py 형식으로 반환해.
  - 빈 결과는 에러가 아니라 빈 배열을 담은 정상 응답이야.
  - 건너뜀 경로(LLM 미호출)를 지원해.
- tests/test_core.py와 tests/test_guardrails.py
  - 빈 입력, 아주 긴 입력, "이전 지시를 무시해" 같은 인젝션 문장, 스토리와 무관한 문장,
    LLM 예외, LLM 타임아웃, 스키마에 안 맞는 LLM 응답, 원문에 없는 근거가 섞인 응답
  - 위 경우 모두 정해진 형식으로 반환되는지 확인해.

pytest와 ruff check .가 통과하는지 확인하고, 커밋하고 보고한 뒤 멈춰.

## 4단계: 다섯 모듈 스키마 초안과 공개 함수

내 확인을 받은 뒤 진행해.

- 각 모듈의 schema.py에 pydantic v2 모델을 만들어. 0단계의 필드 비교표와 2단계 매핑 결정을 따라.
- 명세에서 확인된 규칙은 반영해: NLCD 항목마다 근거(evidence), 해당 내용이 없으면 빈 배열.
- 확인할 수 없는 필드는 만들지 말고 TODO 주석으로 무엇을 확인해야 하는지 적어.
- 각 모듈의 module.py에 공개 함수 하나씩: run_nlcd, run_rex, run_aiq, run_scds, run_ssm.
  내부에서 run_module을 쓰고, prompt.py에는 한두 줄짜리 자리표시 프롬프트만 둬.
- scds/rules.py와 ssm/chunking.py는 3단계에서 정한 경계에 맞춰 함수 뼈대만.
- src/prolog_ai/**init**.py에서 공개 함수 다섯 개만 노출해.
- 다섯 함수 모두 USE_FAKE_LLM=1에서 스키마에 맞는 응답을 돌려주는지 테스트해.

pytest와 ruff check .가 통과하는지 확인하고 커밋해.
