## 🔴 1. 서비스 불능

### 1-1. SCDS가 실제 서비스 흐름에서 충돌을 거의 잡지 못한다

SCDS 룰 검출(`modules/scds/rules.py`)은 `WorldRule.violation_keywords`가 사건 내용에 그대로 들어 있을 때만 후보를 만든다. 그런데 이 키워드가 채워지는 경로가 끊겨 있다.

1. **REX가 키워드를 만들지 않는다.** `rex/schema.py`의 `violation_keywords`는 필수가 아니고(기본값 빈 배열) 설명도 없다. 프롬프트(`rex/prompt.py`)도 키워드를 달라고 하지 않는다. 모델이 빼먹어도 그대로 통과한다.
2. **DB에 저장할 곳이 없다.** db.md의 `WorldRules`는 `content`만 있고 `violation_keywords` 컬럼이 없다.
3. **가치관 기반 판정(RULE-01/03/04)이 없다.** 캐릭터 `core_values`만 있고 세계관 규칙이 없으면 후보가 생기지 않는다.
4. **사건의 `character_ids`가 비어 있으면** 세계관 규칙 위반도 후보가 되지 않는다(캐릭터마다 후보를 만드는 구조).

확인: 키워드 없는 규칙, 가치관만 있는 캐릭터("폭력 회피" + "잔혹하게 살해"), 빈 `character_ids` 모두 `no_candidate`.
결과적으로 사용자가 세계관 규칙을 만들 때 키워드를 직접 입력하지 않는 한 SCDS는 항상 `no_candidate`를 돌려준다. 명세·기획의 핵심 시나리오가 동작하지 않는다.

**해결하려면**: ① REX 스키마에서 `violation_keywords`를 필수로 두고 필드 설명을 달아 모델이 반드시 채우게 하고, ② 백엔드 DB에 키워드 컬럼을 추가하고(WARN C3), ③ RULE-01 판정 기준을 기획이 정해야 한다(WARN A2).

### 1-2. SSM 구조 지도가 명세의 구조와 다르게 나온다

SSM은 챕터마다 LLM을 따로 부르고 결과를 이어붙인다(`ssm/module.py`). 명세의 `acts`는 원고 전체 기준(예: 발단 1~8장, 전개 9~30장)인데, 지금 방식에서는 원리상 그렇게 나올 수 없다.

- 챕터마다 "발단"부터 새로 만들어져 `acts`가 챕터 수 × 막 수만큼 쌓인다.
- LLM은 자기가 몇 번째 챕터인지 모르므로 모든 노드의 `chapter`가 1로 나온다.
- `edges`는 같은 챕터 안에서만 생긴다. 챕터를 넘는 인과(복선 → 회수)는 표현되지 않는다.

확인: 3장짜리 원고 → `acts = [발단(1), 발단(1), 발단(1)]`, 노드 `chapter = [1, 1, 1]`.
챕터가 여러 개인 원고에서는 결과를 구조 지도 화면에 그대로 쓸 수 없다.

**해결하려면**: MSU `Chapter(chapter_no, content)` 목록을 입력으로 받아 챕터 번호를 프롬프트에 넣고, 막(acts)은 챕터별 요약을 모은 뒤 전체 기준으로 한 번 더 판단하는 두 단계 구조가 필요하다(WARN A10, T6).

### 1-3. REX가 규칙을 뽑지 못한다 (프롬프트·스키마 설명 부재)

다섯 모듈 프롬프트가 모두 한 줄짜리이고, LLM에 넘기는 JSON 스키마(`model_json_schema()`)에도 필드 설명(`description`)이 하나도 없다. 모델은 "무엇을, 어떤 기준으로" 뽑아야 하는지 모른다.
지금까지 딱 한 번 실제로 호출했을 때(WARN "실제 호출 결과") REX는 명세 예시 원문에서 규칙을 **0개** 뽑았다. 사례가 하나뿐이긴 하지만, REX가 규칙을 못 뽑으면 1-1의 SCDS까지 같이 멈추므로 불능 등급으로 둔다.
NLCD·AIQ·SSM은 결과는 나오지만 명세 예시와 표현이 다르다(🟡 2-1).

## 🟠 2. 조건부 불능

### 2-1. 긴 원고(완성 원고)에서 REX·AIQ·SSM이 실패한다

MSU 명세상 원고는 "완성 원고 파일 업로드"까지 받는 작품 전체 단위다. 그런데:

- **REX**는 원고 전체를 LLM 한 번에 넣는다.
- **AIQ**는 질문마다 원고 전체를 넣고, `selection`이면 선택 구간을 **한 번 더** 붙인다(10만 자 원고에 10자 선택 → 프롬프트 100,069자).
- **SSM**은 "제N장/N장" 제목이 없으면("1화" 등) 원고 전체가 청크 하나가 된다.

장편 웹소설(수십만 자)은 모델의 입력 한도를 넘거나, 30초 시간 제한 안에 끝나지 않거나, 출력 한도(`MAX_OUTPUT_TOKENS = 4096`)에 걸린다. 입력 한도 초과(4xx)는 바로 `AI_*_FAILED`가 되고, 시간 초과는 같은 요청을 3번 되풀이한 뒤(약 1분 30초) `AI_*_TIMEOUT`이 된다. **긴 원고일수록 매번 실패한다.**

**해결하려면**: REX는 챕터 단위로 나눠 호출하고(그러면 `source_chapter`도 채울 수 있다, WARN A6), AIQ는 선택 구간 주변 문맥만 넣고 전체 원고는 요약이나 검색으로 대신하며, SSM은 1-2의 챕터 목록 입력으로 바꾼다.

### 2-2. SCDS AI 분석 결과가 통째로 버려질 수 있다

AI가 지어낸 충돌을 막으려고 `_keep_candidate_conflicts`가 `(character_id, conflict_target)`이 룰 후보와 **정확히 같은** 충돌만 남긴다(공백·따옴표만 무시). 그런데 프롬프트는 `conflict_target`을 그대로 옮겨 적으라고 지시하지 않는다. 모델이 규칙 설명을 조금만 바꿔 써도("~없다" → "~없음") 그 충돌은 사라진다.

확인: 모델이 `conflict_target`을 한 글자 다르게 쓰면 `status: completed`, `conflicts: []`, `removed_conflict_count: 1`.
SCDS AI 분석 경로는 실제 API로 한 번도 돌려본 적이 없다(evals 케이스가 `no_candidate`에서 끝남). 룰이 후보를 잡아도 사용자에게는 "충돌 없음"으로 보일 수 있다.

**해결하려면**: 모델이 문자열을 다시 쓰지 않게 후보 번호(index)를 고르게 하고, `conflict_target`은 패키지가 후보에서 채워 넣는다.

### 2-3. 백엔드가 `HTTP_STATUS[code]`를 그대로 쓰면 죽는다

`SCHEMA_VALIDATION_FAILED`(모델 응답이 스키마와 안 맞을 때, 드물지 않음)는 `HTTP_STATUS`에 없다. 확인: `HTTP_STATUS["SCHEMA_VALIDATION_FAILED"]` → `KeyError`.
README에 `.get(code, 502)`로 쓰라고 적혀 있지만 연동하는 쪽이 놓치면 요청 처리 중 500이 난다. 패키지가 명세 코드(`AI_*_FAILED`)로 바꿔 보내면 근본적으로 없어진다(WARN A4).

### 2-4. FastAPI `async def` 안에서 직접 호출하면 서버 전체가 멈춘다

공개 함수는 동기 함수이고, 호출 한 번이 최악 약 4분 40초(90초 × 3회 + 대기) 걸린다. 백엔드가 `async def` 엔드포인트 안에서 그대로 부르면 이벤트 루프가 막혀 **그동안 다른 요청도 전부 멈춘다.** handoff.md는 "워커에서 호출하라"고만 적혀 있다. 워커 큐(Celery/RQ 등)나 `run_in_threadpool`로 호출해야 한다는 점을 백엔드와 확실히 맞춰야 한다.

### 2-5. DB에 AI 결과를 저장할 곳이 없다 (저장소 밖)

db.md에는 근거(`evidence`), 감정 키워드, 영향 관계, 작업(job) 상태, `violation_keywords`를 저장할 컬럼·테이블이 없다(WARN C1~C3). 패키지가 결과를 돌려줘도 백엔드가 저장하거나 폴링 상태를 관리할 수 없다. 연동 전에 DB 설계가 먼저 바뀌어야 한다.

> 참고: NLCD가 캐릭터 이름을 뽑지 않는 문제(WARN A1)는 ASS에 초안 이름 수정 API(`PATCH character-drafts/{id}`)가 있어 사용자가 직접 입력할 수 있으므로 불능으로 보지 않았다.
